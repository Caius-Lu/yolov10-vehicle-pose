# Vehicle Pose 压缩实验复盘：演讲稿

> 面向算法工程师；建议总时长 8–10 分钟。PPT 演讲者备注与本文同源。

## 第 1 页｜实验全景：先统一评判标准

**建议时长：2 分 30 秒**

**讲述目标：** 让听众先理解实验规模、统一口径和双门禁，避免只看某一个漂亮数字。

### 逐字稿

这一页先回答两个问题：我们到底试了什么，以及什么结果才算真正成功。

整个项目只讨论模型压缩和结构剪枝，不引入 TensorRT。实验覆盖了部署态分支裁剪、骨干和颈部轻量化、检测与姿态塔减深、ClassLite 分类塔，以及对应的监督恢复和知识蒸馏。评估始终使用同一套三门禁：第一，速度必须在同进程 paired AB/BA 条件下提升至少 10%；第二，精度不能低于基线 Box mAP 0.64761、Pose mAP 0.49455；第三，峰值 CUDA 显存必须可复现地下降。

这里必须强调：参数量和 FLOPs 只是结构指标，不是 latency 的可靠代理。实验里有参数减少超过一半、但真实推理反而没有加速的路线。原因包括 tensor slicing、定向搬运、padding 和 kernel launch 行为变化。因此，所有速度结论都来自 fused FP16、batch 1、640 输入下的 paired 实测，绝不跨进程拼接两个数字。

精度则来自完整 3,606 张图、11,569 个实例的验证集，至少同时看 Box、Pose、PCK 和 NME。内存由独立进程测量模型加载、输入后和推理峰值，避免训练显存与推理显存混用。

从实验地图看，大部分结构剪枝都在速度或精度门禁前停止。新增的 P5-Zero 改变了最终结论：它只移除 backbone P5 和 neck P5 的内部 bottleneck，完整保留 P3、P4 和三个任务塔；最终同时通过速度、精度和显存门禁。右侧两组因此分别代表体积优先的 deployment-only 和速度—精度平衡的 P5-Zero。

### 讲述提醒

- 不要说“已经同时完成速度、精度和显存目标”。
- “部署态体积方案”与“结构加速方案”必须按各自收益边界定性。
- 若被问到延迟绝对值，先说明只有同一次 paired 测量中的相对值可比较。

## 第 2 页｜最佳两组：体积优先与速度—精度平衡

**建议时长：3 分钟**

**讲述目标：** 用统一门禁突出两组可交付结果，并说明各自适用目标。

### 逐字稿

左侧是当前可以交付的 deployment-only 分支裁剪。它删除部署时不需要的一对多分支，参数量下降 26.96%，文件体积下降 26.59%，峰值显存下降 8.99%。完整验证精度保持在 Box 0.665、Pose 0.514，输出做到 bit-exact。

但它不是速度方案：paired latency 只改善 0.19%，没有达到 10% 门槛。因此它的正确定位是精度等价的体积和内存压缩，适合先进入工程交付，而不能宣传为推理加速。

右侧是 P5-Zero 平衡结构。它保留 LitePSA、P3/P4 和完整的 Box、Class、Pose 塔，只把 backbone P5 与 neck P5 两个 C2f 的内部 bottleneck 数量设为零。权重迁移采用投影折叠，605 个张量直接复制、2 个张量折叠，无 missing 或 unexpected key。

最终 paired fused-FP16 延迟从 5.94537 毫秒下降到 5.06345 毫秒，提升 14.83371%；fused 参数下降 15.14%。完整 3,606 图验证得到 Box 0.66254、Pose 0.49592，分别高于门槛 0.01493 和 0.00137。模型驻留显存下降 6.29%，推理峰值显存下降 5.02%，所以三门禁全部通过。

所以这两组形成清晰分工：deployment-only 的参数和文件收益更大，并保持输出 bit-exact；P5-Zero 提供显著速度提升，同时保持门槛以上的 Box/Pose 精度。两者都可交付，但目标不同。

### 可能追问

**为什么选择 P5，而不是继续压缩 P3/P4 或任务塔？**

P5 处于低分辨率语义层，减少串行层能降低 kernel 数量，同时对高分辨率定位细节和分类置信度破坏更小。

**Pose 余量较小，是否可靠？**

当前门禁内通过，但余量只有 0.00137；因此报告明确限定为 RTX 3090 Ti、PyTorch fused FP16 的当前验证口径，换硬件或数据版本必须重跑三门禁。

**现在应该选哪组？**  
若目标是极致体积且不要求显著加速，选 deployment-only；若目标是速度、精度和显存综合平衡，选 P5-Zero。

## 第 3 页｜工程决策：通过三门禁，固化可复用交付

**建议时长：2 分 30 秒**

**讲述目标：** 给出可执行决策、可靠性边界和下一轮结构搜索方向。

### 逐字稿

复盘后有三个核心失败机制。

第一，参数量不是 latency 代理。某些方案虽然参数减少很多，实际 kernel 行为却没有改善。第二，分类塔减深会同时影响检测框置信度和姿态任务，因此不适合作为这次的主压缩点。第三，低分辨率 P5 层减少串行 bottleneck，能在保留 P3/P4 定位细节和完整任务塔的同时获得稳定速度收益。

这些结果沉淀成三条工程规则。第一，冻结参数不等于冻结运行行为，必须同时固定 BatchNorm running statistics。第二，拒绝简单 tensor slicing，权重迁移必须按结构语义处理，包括 C2f 投影折叠、定向搬运和必要的 padding。第三，先跑速度 gate，再决定是否投入训练；所有延迟都做 paired AB/BA，避免时钟和系统状态偏差。

交付阶段冻结 P5-Zero 结构、训练配置和最终 checkpoint，并在目标设备重新执行三门禁。后续探索只做小步消融：每次只改变一个串行深度点，先跑 paired 延迟，再决定是否训练，最后跑完整精度与独立 CUDA memory。

可靠性边界也要说清楚：latency 是 fused FP16、batch 1、640 输入下的同进程 paired 结果；accuracy 来自完整 3,606 图和 11,569 实例；memory 来自独立进程；CSV、JSON、训练日志和停止原因全部留档。这些口径让结论可审计，但不意味着换硬件后绝对毫秒数不变。

最终决策是：deployment-only 作为精度等价的体积和显存方案继续保留；P5-Zero 作为速度—精度平衡方案进入交付。ClassLite52 保留为失败对照，不再重复微调。

### 收尾句

这轮实验最重要的产出不只是一组数字，而是一套可复用的压缩判定流程：先用真实延迟筛结构，再用完整精度和独立显存决定能否交付。

### 讨论入口

- 若优先交付：确认 P5-Zero checkpoint 与目标平台回归计划。
- 若继续研究：以 P5-Zero 为锚点，只做可回退的小步 kernel-depth 消融。
- 若更换硬件：重新执行 paired latency 与独立 CUDA memory，不复用绝对值。
