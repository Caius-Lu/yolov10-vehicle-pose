# Codex 实战：从一组提示词到可验证的 YOLOPose 训练系统

> 部门分享底稿，建议 35–45 分钟。主角是 Codex 驱动的软件工程过程，YOLOv10 Vehicle Pose 是贯穿始终的真实案例，不是一场单纯的模型结构介绍。

## 分享要回答的三个问题

1. Codex 能否从需求文档出发，跨本地 Mac、远程 Ubuntu、GPU、数据和文档，交付一个完整训练系统？
2. 怎样让 Codex 的输出从“看起来能跑”升级为“有测试、有证据、能复现、知道哪里还没完成”？
3. 人在过程中应该提供什么、检查什么，又应该把什么交给 Codex 自动推进？

## 开场：这不是一次“让 AI 写个 Head”

我给 Codex 的初始输入不是一段具体代码，而是一份使用顺序和 9 个阶段提示词：仓库初始化、数据、设计、实现、转换、训练、评测、性能优化、最终验收。

最终目标是把官方 YOLOv10n 改造成车辆单类、14×3 关键点的训练系统，同时保留原检测能力，并在远程 RTX 3090 Ti 上完成训练和性能验证。

这个任务真正困难的地方不只是 PyTorch：

- 要先读懂一个陌生仓库的真实调用链，而不是按想象修改文件。
- 要保持 YOLOv10 one-to-many 训练和 one-to-one、NMS-free 推理语义。
- 要跨本地与远程环境处理依赖、权重、GPU、数据传输和长任务。
- 要区分 fixture、smoke、baseline 和正式指标，不能把“能跑”说成“有效”。
- 要把整个过程记录成别人可以复查和复现的证据链。

所以这次实践验证的不是“Codex 会不会补全代码”，而是它能不能承担一个受约束的工程闭环。

## 一页结论

Codex 在这个项目中同时承担了六种角色：

| 角色 | 在本项目中的实际动作 | 产物或证据 |
|---|---|---|
| 需求分析与项目管理 | 阅读 00–09 提示词，拆阶段、设门禁、维护执行计划 | 九阶段路线、验收状态 |
| 代码考古与方案设计 | 审计 YOLOv10 task map、Head、Loss、Predictor 与 Validator | `reports/design/` |
| TDD 工程师 | 先定义匹配、gather、空目标、回归等测试，再实现 | 24 个聚焦测试、数据四脚本 84% 分支覆盖率 |
| 远程环境操作员 | 探查 GPU/驱动/PyTorch，建立 venv，同步代码和权重 | bootstrap 报告、命令记录 |
| 数据与实验守门员 | 数据未授权时停止真实训练，不伪造指标；数据到位后校验再解压 | `ACTION_REQUIRED`、数据报告 |
| 技术写作者与审计员 | 每阶段记录命令、偏差、PASS/FAIL/BLOCKED | `reports/`、执行日志、本文 |

我的核心体会是：Codex 的价值不只是减少敲代码时间，而是把“读代码—做决策—实现—验证—记录”串成连续工作流。

## 项目输入：如何给 Codex 一个可执行的目标

初始说明里有四类关键约束：

- 功能约束：车辆单类、14 个关键点，每点 `(x, y, visibility)`。
- 架构约束：保留 YOLOv10n Backbone/Neck 和原 Detect，关键点 Head 使用部署友好的卷积与张量变换。
- 正确性约束：关键点必须使用 bbox assigner 的真实 GT 匹配索引，不能按预测框顺序猜对应关系。
- 工程约束：不伪造数据与指标；修改前读真实代码；每阶段生成报告；性能优化必须做精度回归。

这类提示词的关键不是写得长，而是明确：目标、不可破坏项、完成定义、证据形式和停止条件。

## Codex 的工作方式：一个可审计的闭环

本项目形成了下面这条循环：

```text
需求与边界
    ↓
读取真实仓库和环境
    ↓
提出设计与风险假设
    ↓
先写测试 / 定义验收
    ↓
最小实现
    ↓
本地与远程验证
    ↓
失败定位与单点修复
    ↓
报告、日志、下一阶段门禁
```

Codex 不是每一步都一次成功。真正有价值的是它能保留上下文，从失败输出继续定位，并且不把局部成功包装成最终完成。

## 实际时间线：从空目录到训练系统

### 1. 把自然语言路线变成工程骨架

Codex 首先读取提示词套件，固定上游来源和 commit，创建独立分支与工程目录，把本地工程同步到远程服务器。

真实基线：

- 上游：THU-MIG YOLOv10。
- 固定 commit：`453c6e38a51e9d1d5a2aa5fb7f1014a711913397`。
- 开发分支：`feat/vehicle-pose`。
- 远程环境：Ubuntu 22.04 / WSL2、RTX 3090 Ti 24 GB。

这一步的意义是先固定“从哪里开始”，否则后续所有性能和精度结果都缺少坐标系。

### 2. 没有照着 requirements 机械安装

远端已经有可用的 PyTorch 2.6.0+cu124 和 CUDA 12.4；官方 requirements 固定 PyTorch 2.0.1，而依赖下载实测只有约 22 KB/s。

Codex 没有继续长时间下载并覆盖一个已验证的 CUDA 栈，而是：

1. 验证现有 PyTorch 与 GPU 是否真的可用。
2. 创建 `--system-site-packages` 的项目 venv。
3. 以 editable/no-deps 安装当前仓库。
4. 把这一偏差明确写进 bootstrap 报告。

这里体现的是“可复现不是机械重装”。关键是版本、命令、偏差和验证结果都可追溯。

### 3. 先做代码考古，再决定改法

Codex 沿真实调用链阅读了：模型配置解析、task map、`v10Detect`、双分支 Loss、assigner、Predictor 和 Validator。

最重要的设计发现是：YOLOv10 训练时有 one-to-many 与 one-to-one 两套分支，关键点监督必须继承各自 assigner 的 `target_gt_idx`。如果只给检测框加一个关键点向量，却丢掉匹配关系，训练可以运行，但关键点监督可能错位。

基于审计结果，Codex 设计并实现了：

- P3/P4/P5 三尺度、纯卷积的 14×3 关键点塔。
- one-to-many/top-k=10 与 one-to-one/top-k=1 两套关键点监督。
- 与 bbox 使用同一 anchor top-k 索引的 NMS-free 关键点 gather。
- Pose Trainer、Validator、Predictor 与 task map。
- `one2one_only` 推理快速路径。

技术设计只是案例，值得分享的方法是：让 Codex 先输出仓库审计和变更清单，再允许它修改代码。

### 4. 用测试把“应该正确”变成“可以检查”

项目采用测试先行。测试覆盖了：

- top-k bbox 与 keypoint 是否使用同一索引。
- one-to-many 与 one-to-one Loss 是否都能反向传播。
- 空目标是否安全。
- checkpoint 保存、清理、加载是否闭环。
- 官方 YOLOv10 Detect 是否回归通过。
- 数据转换是否确定性、是否 group 零泄漏。
- PCK/NME 公式是否正确。
- 原路径与 `one2one_only` 输出是否数值一致。

阶段性结果：24 个聚焦测试通过；合并、转换、质量与预览四个数据脚本的合计分支覆盖率为 84%。此外，4 张训练图 + 2 张验证图的生成 fixture 跑完了一个完整 CUDA epoch、两次优化器更新、验证、best/last checkpoint 保存、最终加载和 PCK/NME 文件导出。

这里必须强调：fixture 的 AP 没有业务意义。它只证明 Trainer/Validator/checkpoint 管线接通。

### 5. Codex 如何处理连续出现的真实故障

#### 故障 A：依赖下载极慢

- 现象：固定版本下载约 22 KB/s。
- Codex 动作：终止无价值等待，探查系统已有 CUDA 栈，改建兼容 venv。
- 约束：不隐藏版本偏差，远端 smoke 必须通过。

#### 故障 B：PyTorch 2.6 无法加载官方权重

- 现象：`torch.load` 的 `weights_only` 默认行为变化导致模块 checkpoint 被拒绝。
- Codex 动作：确认权重来自可信官方来源，对项目现有 checkpoint 格式显式使用兼容加载，并保留旧版本 fallback。
- 后续发现：训练完成后的 `strip_optimizer` 也走加载路径，因此同类问题必须在两个入口修复。

#### 故障 C：训练意外触发 W&B

- 现象：服务器已有登录状态，smoke 可能创建外部实验记录。
- Codex 动作：让回调尊重 `WANDB_MODE=disabled`，把离线/禁用行为变成明确配置。
- 教训：AI 代理能操作的外部状态必须有边界，登录态不能等同于授权。

#### 故障 D：数据未到位

- 现象：公开转换仓库没有完整下载器，真实数据不在工程中。
- Codex 动作：停止真实训练，保留 fixture 测试，输出 `BLOCKED_BY_DATASET_AUTHORIZATION` 和明确行动项。
- 教训：可靠代理的重要能力之一，是知道什么时候不能继续宣称完成。

#### 故障 E：32 GiB 数据需要跨设备移动

- 现象：用户补充了本地 OpenDataLab CarFusion 路径。
- Codex 动作：先做轻量元数据探查，确认 503 个文件和主体归档；检查远端空间；计算本地 SHA-256；用可断点续传的 rsync 复制；传后再次校验再解压。
- 教训：长任务也应该有校验点和恢复策略，而不是只执行一条 `scp`。

### 6. Codex 不只实现功能，也主动寻找系统开销

仓库审计发现：上游 `v10Detect.forward()` 在非导出 `eval()` 下仍计算 one-to-many 分支，但 Predictor 最终只消费 one-to-one 结果。

Codex 没有直接删除原路径，而是增加显式 `one2one_only`：训练行为不变，评测时可对同一输入比较两条路径。

短时合成 smoke 结果：

| 路径 | 平均耗时 | P95 | 输出误差 |
|---|---:|---:|---:|
| 原 PyTorch eval | 8.545 ms | 8.794 ms | 基准 |
| `one2one_only` | 6.415 ms | 6.735 ms | 最大误差 0 |

这组数据只证明执行路径优化有效，不代表正式设备性能，也不代表真实数据精度。Codex 在报告中保留了这个边界。

## 交付的不只是模型代码

当前工程已经形成以下可复用资产：

- 模型：Vehicle Pose Head、双分支 Loss、NMS-free 后处理。
- 数据：转换器、质量门禁、group-aware 划分、关键点索引模板。
- 训练：smoke、resume、baseline 入口。
- 评测：bbox 指标、PCK/NME、可见性和尺度分组接口。
- 性能：model-only/end-to-end benchmark、profiler、正确性对比。
- 测试：核心、集成、回归、环境能力测试。
- 文档：架构、数据、训练、评测、优化、验收和执行日志。

这也是 Codex 与普通代码补全工具的区别：它可以围绕目标持续工作，并把旁路脚本、测试和文档一起纳入完成定义。

## 人和 Codex 的职责边界

### 人必须做的事

- 给出业务目标、数据使用权限和不可接受的风险。
- 对关键点语义、左右关系和业务指标做领域确认。
- 决定是否接受环境偏差、训练成本和外部系统写入。
- 审核最终实验结论，而不是只看代码是否生成。

### 适合交给 Codex 的事

- 大范围读取仓库并追踪调用链。
- 把阶段目标拆成代码、测试、命令和报告。
- 在本地与远程之间同步、执行、收集证据。
- 根据报错持续定位并做最小修复。
- 自动维护执行日志和交付文档。

### 不应该让 Codex 自行越界的事

- 绕过数据授权或使用来源不明的数据。
- 未经确认写入外部实验平台、消息系统或生产资源。
- 用 fixture 指标冒充真实训练结果。
- 没有精度回归就宣布性能优化成功。

## 一套可复用的提示词结构

以后让 Codex 构建类似训练系统，可以用下面的五段式：

```text
目标：最终要交付什么系统，服务什么任务。

现状：仓库、远程机器、数据、权重分别在哪里。

约束：哪些能力必须保留；哪些动作禁止；哪些外部写入需要授权。

验收：测试、指标、性能、复现和文档分别达到什么标准。

执行方式：先读取真实代码和环境；分阶段推进；每阶段报告命令、证据、失败和下一步。
```

比“帮我改成 pose 并训练一下”更重要的是写清楚完成定义和证据要求。

## 我从这次实践中得到的 Codex 使用原则

1. 让 Codex 先读，后设计，再改代码。
2. 把“不允许破坏什么”写得和“要新增什么”一样清楚。
3. 要求测试和验收命令，不只要求实现。
4. 长任务使用断点续传、日志、哈希和阶段检查点。
5. 明确 fixture、smoke、baseline、正式结果四个等级。
6. 报错不要只贴最后一行，让 Codex读取完整上下文和相关源码。
7. 任何外部写入、凭据和授权都要显式设边界。
8. 要求 Codex 维护执行日志，最终分享材料会自然从证据中生长出来。

## 现场演示建议（8–10 分钟）

### 演示 1：从提示词到执行计划

展示 `00_README_使用顺序.md`，说明只有目标和阶段约束，没有现成实现；再展示 Codex 如何形成计划和工程目录。

### 演示 2：让 Codex 用代码回答架构问题

打开仓库审计、`v10Pose` Head 和 Loss，重点展示 `target_gt_idx` 如何把 bbox 匹配传给关键点，而不是逐行讲网络。

### 演示 3：展示一次失败后的连续修复

用 PyTorch 2.6 `weights_only` 或 W&B 案例，展示“日志 → 定位入口 → 回归测试 → 文档记录”的闭环。

### 演示 4：展示证据，不只展示最终图片

依次打开测试结果、短时 benchmark、数据哈希与执行日志。强调哪些是 PASS、哪些仍是 BLOCKED、哪些结果不能外推。

## 最终结果：系统完成，但不隐藏数据边界

所有真实数据门禁已经完成：数据转换与质检、smoke、32 图过拟合、200 epoch baseline、最终评估、benchmark 和 100 图可视检查。

| 指标 | 最终结果 |
|---|---:|
| 验证集 | 3,606 图 / 11,569 个实例 |
| Box mAP50 / mAP50-95 | 0.818 / 0.665 |
| Pose mAP50 / mAP50-95 | 0.765 / 0.515 |
| PCK@0.05 / PCK@0.10 | 0.6686 / 0.8525 |
| NME | 0.05960 |
| 可见 / 遮挡 PCK@0.05 | 0.6875 / 0.5470 |

训练在 epoch 176 遇到 WSL 重启和 E 盘暂时丢失。Codex 没有启动第二个任务，而是确认进程、挂载、checkpoint 和 `results.csv` 后从 `last.pt` 续跑。最后 25 个 epoch 用时 1.230 小时，按该段速度估算 200 epoch 的有效 GPU 训练约 9.84 小时；实际墙钟时间还包含机器离线和存储恢复，不能混为一谈。

还有一个必须公开的限制：模型保持 14×3 输出，但转换质检显示索引 13 在全部 62,434 个实例中可见性均为 0，因此这一点没有监督，也没有 PCK/NME。准确说法是“14 点张量接口、当前 CarFusion 版本有 13 个可监督/可评估点”。

## 可视化不是装饰，而是指标之后的门禁

第一次查看原图预测时，关键点大体合理，但 16:9 图片上的框明显过大；Validator 自带图片却正常。这种矛盾说明问题不在训练权重，而在 Predictor 路径。

Codex 先补回归测试，捕获后处理前仍为 `xywh` 的框，再定位到 `YOLOv10PosePredictor.postprocess` 缺少 `xywh2xyxy`。最小修复后：

- Vehicle Pose 回归 9/9 通过；
- 重新生成固定 100 图预测；
- 宽图、边缘截断、遮挡和多车样本的框与关键点均恢复一致；
- baseline 训练和 Validator 指标不变，因为缺陷只在 raw Predictor 路径。

这段经历比“一次训练成功”更值得分享：指标、可视化和两条代码路径要互相校验，AI 代理也必须接受视觉门禁。

## 耗时优化：先解决系统瓶颈，不急着牺牲精度

修复后的同口径端到端 benchmark 显示，JPEG 路径输入到 `Results` 的平均耗时为 60.10 ms，而框架记录的核心预处理、推理和后处理之和明显更小。结合训练中 E 盘 I/O 卡顿，最先验证的不是 FP16/INT8，而是数据位置。

Codex 将同一批 100 张图片复制到 WSL ext4，逐文件 SHA-256 校验 0 差异，并保持 checkpoint、模型、图片、batch 和迭代数完全一致：

| 数据位置 | 平均延迟 | 平均 P95 | FPS |
|---|---:|---:|---:|
| `/mnt/e` Windows 文件系统 | 60.10 ms | 109.25 ms | 16.64 |
| WSL ext4 | 16.63 ms | 18.62 ms | 60.12 |
| 改善 | **−72.3%** | **−83.0%** | **3.61×** |

这个方案只改变文件位置，因此不会降低模型精度。独立脚本 `scripts/stage_carfusion_to_wsl.sh` 会解引用复制、做 SHA-256 门禁并生成新的 runtime YAML；原 baseline 数据、代码、checkpoint 和输出目录均不修改。

Microsoft 的 WSL 文档也建议 Linux 命令行工作负载把文件放在 WSL 文件系统以获得更好性能：[Working across Windows and Linux file systems](https://learn.microsoft.com/en-us/windows/wsl/filesystems)。下一阶段才值得在本地化数据上测量 `workers`、`persistent_workers` 和 `prefetch_factor`；TensorRT FP16 则必须另做精度回归，不能与零精度损失的数据本地化混为一谈。

## 到这里，Codex 实际完成了什么

- 从提示词套件建立工程骨架、约束、门禁和证据目录。
- 阅读真实 YOLOv10 调用链，设计并实现双分支 Vehicle Pose。
- 用测试驱动核心匹配、Loss、checkpoint、Predictor 和回归行为。
- 操作 wsl-dev 完成数据校验、远程训练、断点恢复、评估与性能实验。
- 在指标之后执行 100 图视觉门禁，并修复只有原图 Predictor 才暴露的问题。
- 识别 `/mnt/e` 系统瓶颈，用独立、零精度损失方案取得 3.61× 端到端提升。
- 把成功、失败、假设、限制、命令和产物整理成可复现的部门分享材料。

## 结束语

这次 YOLOPose 项目让我看到，Codex 最有价值的使用方式，不是把它当作“更快的程序员”，而是把它放进一个有边界、有测试、有远程执行能力、有证据链的工程流程里。

当输入只说“写代码”时，它交付代码；当输入同时定义目标、约束、验收和记录方式时，它才有机会交付一个系统。
